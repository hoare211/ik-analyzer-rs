## 1. 概览与名词

ik-analyzer-rs 承袭 IK Analyzer 的算法结构，但**不是 u6 的逐字移植**：实现基准是
analysis-ik（吸收其缺陷修复），默认配置按产品需要自行取舍；只有在显式调用
`Config::u6_parity` 时，才切换到与 u6 同配置同输出的兼容口径（见 §6.4）。

| 名词 | 含义 |
|---|---|
| **TokenizerFactory** | 分词器工厂。负责**一次性加载词典**，之后可廉价地创建无数个分词器实例。推荐的总入口。 |
| **IKSegmenter** | 分词器实例，实现了 `Iterator<Item = Lexeme>`，逐个产出词元。 |
| **Config / ConfigBuilder** | 分词配置（是否 smart、用哪些词典）。`ConfigBuilder` 提供链式 API。 |
| **DictSource** | 词典来源：要么文件 `DictSource::File(path)`，要么内存文本 `DictSource::Text(text)`。 |
| **Lexeme** | 一个词元：包含文本、起止位置、词元类型。 |
| **smart / fine 模式** | smart = 歧义消解（粗粒度，更贴近语义）；fine = 细粒度（尽可能多切）。 |
| **扩展词典 vs 主词典** | 主词典是 IK 自带主词表；`add_ext_*` 是**追加**到主词典之上，不影响默认主词表。 |

## 2. 安装与引入

### 2.1 Rust 库

在 `Cargo.toml` 加入：

```toml
[dependencies]
ik-analyzer-rs = "1.3.0"
```

> 注意：仓库内 `[lib]` 名是 `ik_analyzer`，但发布到 crates.io 的包名是 `ik-analyzer-rs`。导入时用 `use ik_analyzer::...;`（即 lib 名）。

### 2.2 Python 绑定

见 [第 13 节](#13-python-绑定)。从 PyPI 安装：

```bash
pip install ik-analyzer-py
```

从源码构建需 `maturin`：

```bash
cd python
maturin develop --release        # 安装到当前虚拟环境
# 或打 wheel：
maturin build --release
```

### 2.3 命令行工具

见 [第 12 节](#12-命令行工具cli)，仓库内可直接 `cargo run`。

## 3. 核心概念

```
ConfigBuilder ──build()──▶ Config
                              │
                   TokenizerFactory::new(config)
                              │   （仅这一步会加载词典，较重）
                              ▼
                   TokenizerFactory  (共享 Arc<Dictionary>)
                              │
            ┌─────────────────┼───────────────────────┐
            ▼                 ▼                        ▼
   factory.segmenter(text)  factory.segmenter_from_read(r)   factory.dictionary()
            │   （极轻量，每句文本一次）
            ▼
      IKSegmenter (Iterator<Item = Lexeme>)
```

**最关键的一点**：`TokenizerFactory` 只应在**应用启动时创建一次**（它要读词典、建 Trie，开销大）；之后对每条文本调用 `factory.segmenter(text)` 非常廉价。

## 4. Rust 快速开始

```rust
use ik_analyzer::{Config, TokenizerFactory};

fn main() {
    // 1) 用默认配置建工厂（默认 use_smart = true）
    let factory = TokenizerFactory::new(Config::builder().use_smart(true).build());

    // 2) 对文本分词，得到迭代器
    let mut seg = factory.segmenter("欢迎使用本分词器");

    // 3) 逐个取词元
    assert_eq!(seg.next().unwrap().text(), "欢迎");
    assert_eq!(seg.next().unwrap().text(), "使用");

    // 或一次性收集为 Vec<String>
    let words: Vec<String> = factory
        .segmenter("中华人民共和国")
        .map(|l| l.text().to_string())
        .collect();
    println!("{:?}", words); // ["中华人民共和国"]
}
```

`IKSegmenter` 实现了 `Iterator`，所以可以直接 `for lexeme in factory.segmenter(text) { ... }`。

## 5. 两种分词模式

通过 `ConfigBuilder::use_smart(bool)` 控制：

```rust
let smart = TokenizerFactory::new(Config::builder().use_smart(true).build());
let fine  = TokenizerFactory::new(Config::builder().use_smart(false).build());

let text = "张三说的确实在理";

let s: Vec<String> = smart.segmenter(text).map(|l| l.text().to_string()).collect();
let f: Vec<String> = fine.segmenter(text).map(|l| l.text().to_string()).collect();

println!("smart: {:?}", s); // ["张三", "说的", "确实", "在理"]
println!("fine : {:?}", f); // ["张三", "三", "说的", "的确", "确实", "实在", "在理"]
```

- **smart（默认）**：歧义消解，输出更贴近语义的粗粒度结果。
- **fine（细粒度）**：保留所有切分可能，适合建索引、需要召回率的场景。

两种方式的分词质量与原版 IK Analyzer 一致（见 §6.4）。

## 6. 配置详解

### 6.1 `DictSource`：词典来源

```rust
pub enum DictSource {
    File(PathBuf),            // 从文件加载
    Text(Cow<'static, str>),  // 从内存字符串加载（每行一个词）
}
// 便捷构造
DictSource::text("词1\n词2")          // &'static str，零拷贝
DictSource::text_owned("动态".into()) // 运行时 String
```

`Text` 来源让单测、嵌入、动态词典**无需落盘文件**即可注入。

### 6.2 `ConfigBuilder` 方法一览

> `ConfigBuilder` 是**链式**的：每个 setter 返回 `self`，可连续调用，最后 `.build()`。

| 方法 | 作用 |
|---|---|
| `use_smart(bool)` | 设置分词模式（默认 `true`，同 v1.0.0 / 2012_u6） |
| `enable_lowercase(bool)` | 大小写策略（默认 `true` = ASCII 大小写不敏感；`false` = 严格大小写敏感） |
| `astral_mode(AstralMode)` | 补充平面字符处理模式（默认 `AstralMode::Ideographs`，见 §6.5） |
| `with_main_dict(Vec<DictSource>)` | **整部替换**主词典（覆盖 IK 默认主词表） |
| `with_quantifier(Vec<DictSource>)` | **整部替换**量词词典 |
| `with_stop_words(Vec<DictSource>)` | **整部替换**停用词词典 |
| `add_ext_dict_paths(Vec<PathBuf>)` | 追加扩展主词典（文件路径列表） |
| `add_ext_dict_text(&str)` | 追加扩展主词典（静态文本） |
| `add_ext_dict_owned_text(String)` | 追加扩展主词典（运行时文本） |
| `add_ext_stop_word_paths / _text / _owned_text` | 追加扩展停用词（同上三种） |
| `add_ext_quantifier_paths / _text / _owned_text` | 追加扩展量词（同上三种） |

> **关键点**：`with_*` 会**替换**对应的默认词典；`add_ext_*` 是**追加**到默认词典之上。绝大多数定制用 `add_ext_*` 即可，保留 IK 自带主词表。
>
> **另有一个非构建器的完整配置构造器**：`Config::u6_parity(use_smart)` ——
> 冻结的 IK 2012_u6 口径预设，见 §6.4。

### 6.3 示例

**追加自定义词典文件：**

```rust
let factory = TokenizerFactory::new(
    Config::builder()
        .use_smart(true)
        .add_ext_dict_paths(vec![PathBuf::from("custom/long_word_dict.dic")])
        .build(),
);
```

**完全用内存词典（无文件、无 IK 默认主词表）：**

```rust
let factory = TokenizerFactory::new(
    Config::builder()
        .use_smart(true)
        .with_main_dict(vec![DictSource::text("深度学习\n自然语言处理")])
        .build(),
);
```

**追加内存停用词：**

```rust
let factory = TokenizerFactory::new(
    Config::builder()
        .add_ext_stop_word_owned_text("的\n了\n嘛".to_string())
        .build(),
);
```

**混合（文件 + 内存）：**

```rust
let factory = TokenizerFactory::new(
    Config::builder()
        .add_ext_dict_paths(vec![PathBuf::from("dict/a.dic"), PathBuf::from("dict/b.dic")])
        .add_ext_dict_owned_text("临时热词".to_string())
        .build(),
);
```

> 词典文件按行读取，每行一个词（首尾空白裁剪口径 = u6 `String.trim()` 的码点 ≤ U+0020 **外加 U+00A0（NBSP）**，并剥离可能的前导 UTF-8 BOM `U+FEFF`——Windows 编辑的 `.dic` 常见，u6 不剥离会污染首词条；注意 **U+3000 等其余 Unicode 空白不裁剪**，与 u6 一致，裁剪会静默改变词条集合）；大小写按 `enable_lowercase` 在**DAWG 构建期**做 ASCII 归一（默认小写化）；非法行会 `warn` 跳过而非崩溃（见 `src/dic/dictionary.rs`）。

### 6.4 与 IK 2012_u6 的行为 parity 契约

**本节描述的是一项按需开启的兼容能力，不是本库的默认定位。**

| 层 | 定位 |
|---|---|
| 实现层 | 以 **analysis-ik**（`master@6d2d70f`）为基准：吸收其相对 u6 的缺陷修复，其行为变更实现为可配置机制 |
| 行为层（默认输出） | 独立的产品决策，**可优于 u6**（默认停用词表、CJK 扩展 B–I 等） |
| 兼容层（按需开启） | `Config::u6_parity` 提供显式契约，供需要与 u6 完全一致的下游使用 |

> **Parity 契约**：**仅当显式启用 `Config::u6_parity` 时**，对同一份「有效配置」
> （`useSmart` × 大小写策略 × 停用词集 × 词典集 × astral 模式），本库的词元序列
> （文本 + 类型 + 相对顺序）与 u6 逐字一致。
> 契约**不靠默认值巧合**保证，而靠：① 显式预设 `Config::u6_parity`；
> ② 下面的配置映射表；③ golden 差分测试（工装 `testing/ab/`）。
> 默认配置下不承诺该一致性。

**配置映射表**（每种 u6 装配 ↔ 本库配置）：

| u6 装配 | 本库对应配置 |
|---|---|
| bare core（无 cfg.xml，无停用词） | `Config::u6_parity(use_smart)` |
| jar 分发（`ext.dic` + 32 英文停用词） | 默认配置 + `with_stop_words(u6 `stopword.dic` 的内容)` |

```rust
// IK 2012_u6 口径：u6 分发词典 + 无停用词 + 大小写不敏感 + astral 丢弃
let factory = TokenizerFactory::new(Config::u6_parity(true));
```

`u6_parity` 钉住一份**冻结**配置：主词典 = u6 分发词表（`main2012.dic` +
`ext.dic` + `quantifier.dic`，经 `u6_dict_sources()` 直接引用，未来默认词表
扩容不破坏它）+ 停用词置空 + `enable_lowercase=true` + `AstralMode::Drop`。
需要「u6 + 自定义词」时用 `with_main_dict` 显式装配，并自行承担 parity 责任。

**默认配置与 u6 的差异**（全部可配置、默认关闭或已披露）：

| 维度 | 默认行为 | 与 u6 的关系 |
|---|---|---|
| `use_smart` | `true` | u6 core 构造器必传、本身无默认；smart/fine 双口径均已 0 分歧背书 |
| `enable_lowercase` | `true` | = u6 无条件 ASCII 小写 |
| 停用词表 | 内置 102 词默认过滤（33 英文 = u6 分发 / analysis-ik 默认口径，与 u6 `stopword.dic` 逐字节相同；69 中文 = 本项目增强） | 产品增强；`u6_parity` / `with_stop_words(vec![])` 置空即 u6 口径 |
| astral 字符 | `AstralMode::Ideographs`：CJK 扩展 B–I 识别为汉字，emoji 丢弃 | u6 因 Java `char` 局限全部丢弃；`AstralMode::Drop` 即 u6 口径（见 §6.5） |
| CJK 门控 | 非 `CHAR_USELESS` 即推进词典匹配（`A股`/`K线` 等 9 个混合词条可达） | 与 u6 / analysis-ik 一致（2026-09-27 问题记录 §1 的修复） |
| 全角大写 `regularize` | else-if：`Ａ` → `A`，不叠加小写 | 与 u6 / analysis-ik 逐字一致（问题记录 §2 的修复） |
| 词典侧大小写 | ASCII 折叠（构建期，与 `enable_lowercase` 联动） | u6 为 Unicode `toLowerCase()`；默认词典上两种口径**不可观测**（276,135 词审计：不存在 `Unicode 小写 ≠ ASCII 折叠` 的词） |

**例外清单**（u6 自身缺陷或表示层差异，均已披露；修复/差异不视为 parity 违背）：

| # | 例外 | 性质 |
|---|---|---|
| 1 | >4096 字符换页：u6 每页边界重复输出 1 个重叠 token，本库不重复 | u6 缺陷修复（A 级实测） |
| 2 | 带 BOM 的词典：u6 污染首词条，本库剥离前导 `U+FEFF` | u6 缺陷修复 |
| 3 | `sat_mul` 路径权重乘法：u6 `int` 连乘可静默溢出，本库饱和到 `i32::MAX` | 纯稳健性；u6 词典下不可达 |
| 4 | `offset` 单位：本库为**码点**，Java 为 UTF-16 码元（Python 绑定为 byte 偏移） | 表示层；词元文本/类型序列一致，差分工具侧换算（BMP 1:1，astral 1→2） |
| 5 | 数量词链式合并（`compound` 两个独立 `if`）：u6 误写 `if/else if` 漏合并 | u6 缺陷修复（`42三首` 可合并） |
| 6 | 词典行首尾空白裁剪：除 u6 `trim()` 口径（≤U+0020）外**追加裁 U+00A0（NBSP）**，尾附 NBSP 的词条（如 `方正凤凰城\u{a0}{4}`）u6 不可命中、本库可命中；U+3000 等其余 Unicode 空白**不裁**（= u6，裁剪会静默扩充词条集合） | 有意改进（issue 20261012 §7.4 声明保留；U+3000 不裁是 2026-10-12 修复） |

**对账结论**（9133 行语料 × {smart, fine} × {默认, Java 口径} 四口径 0 分歧，
装配见《问题记录-大小写全角与词典匹配差异.md》§4/§5）：

- **细粒度模式：9133 行逐行 0 分歧**（`segment_dump --smart false --no-stop-words`）；
- **smart 模式：仅 1 行分歧**（第 5128 行），即上表「数量词两轮合并」——u6 自身
  缺陷所致；
- 默认（停用词启用）下与 u6 bare-core 口径的差异 **100% 可由「停用词 token
  被过滤」解释**，无其它语义漂移。

```bash
# 命令行对账（逐行输出 token，diff 用）
cat benches/corpus.txt | cargo run --release --example segment_dump -- --no-stop-words
```

### 6.5 `AstralMode`：补充平面字符处理

补充平面（astral，码点 > U+FFFF）字符包括 emoji、符号与 CJK 扩展 B–I 汉字。
u6 与 analysis-ik 均以 Java `char`（UTF-16 码元）工作：u6 全部丢弃，
analysis-ik 经 `SurrogatePairSegmenter` 输出（但有两个已实证缺陷——单字母
ENGLISH 紧邻代理对时丢失、跨页代理对被拆成半个）。本库以 Rust `char`
（标量值）直接处理，行为由三值枚举显式选择：

| 变体 | 行为 |
|---|---|
| `AstralMode::Drop` | 全部非 BMP 字符丢弃（**= u6 严格口径**；`Config::u6_parity` 钉此值） |
| `AstralMode::Ideographs` | **默认**：CJK 扩展 B–I 识别为汉字（可参与词典匹配），其余（emoji 等）丢弃 |
| `AstralMode::Tokens` | 全部非 BMP 字符输出为单字 `CNCHAR` 词元（机制对齐 analysis-ik 的目标，但不照搬其缺陷） |

```rust
let factory = TokenizerFactory::new(
    Config::builder().astral_mode(AstralMode::Tokens).build(),
);
// "你好😀世界" => ["你好", "😀", "世界"]
```

**实现保证**（相对 analysis-ik 的改进，均为 A 级实测背书）：
① 紧邻 astral 的单字母 ENGLISH 不丢失（B 会丢）；
② astral 字符跨 4096 换页不会被拆成半个（B 会把高位代理单独输出为脏 token，
Rust `char` 模型天然规避，`test_astral_across_buffer_boundary` 固化）；
③ astral 字符可参与词典匹配（B 的 `SurrogatePairSegmenter` 完全不做词典匹配）。

## 7. `Lexeme` 输出与词元类型

`IKSegmenter` 产出的是 `Lexeme`，不只是字符串。如需位置/类型信息，用 `Lexeme` 的方法：

| 方法 | 返回 | 含义 |
|---|---|---|
| `text()` | `&str` | 词元文本 |
| `begin_position()` | `i32` | 绝对起始位置（字符偏移） |
| `end_position()` | `i32` | 绝对结束位置 |
| `length()` | `i32` | 词元长度（字符数） |
| `offset()` | `i32` | 缓冲偏移（多缓冲场景用） |
| `lexeme_type()` | `i32` | 词元类型常量（见下表） |

**词元类型常量**（与原始 IK 逐一对应）：

```rust
Lexeme::TYPE_UNKNOWN   = 0
Lexeme::TYPE_ENGLISH   = 1
Lexeme::TYPE_ARABIC    = 2
Lexeme::TYPE_LETTER    = 3
Lexeme::TYPE_CNWORD    = 4    // 中文词
Lexeme::TYPE_CNCHAR    = 64   // 单个中文字
Lexeme::TYPE_OTHER_CJK = 8    // 其他 CJK（日韩等）
Lexeme::TYPE_CNUM      = 16   // 中文数字
Lexeme::TYPE_COUNT     = 32   // 量词（如"个""斤"）
Lexeme::TYPE_CQUAN     = 48   // 中文数词+量词组合
```

**示例：带位置与类型：**

```rust
for lex in factory.segmenter("张三123公斤") {
    println!(
        "[{}] begin={} end={} type={}",
        lex.text(),
        lex.begin_position(),
        lex.end_position(),
        lex.lexeme_type(),
    );
}
```

> 生僻字（含补充平面 `𪚥` U+2A6A5 等）会被正确识别为汉字（CJK），不会像原版那样被拆成代理对丢弃（见 §6.4 例外清单）。

### 7.1 零拷贝入口：`segment_spans`（推荐用于检索/索引）

`segmenter()` 会为**每个输出词元**做一次 `String` 分配以生成文本。
实测这占分词热路径**全部堆分配的 94%**（`benches/corpus.txt`：288,712 字符 /
202,231 词元 → 205,307 次分配中约 202,231 次来自这里，可用
`examples/alloc_count.rs` 复核）。

若你只需位置与类型（切片、索引、Offsets 映射等），用 `segment_spans()`：

```rust
use ik_analyzer::{Config, TokenizerFactory, char_to_byte_map};

let factory = TokenizerFactory::new(Config::builder().build());
let text = "欢迎使用本分词器";

// 整篇只需构建一次 char→byte 映射，供全部 span 复用
let map = char_to_byte_map(text);

let words: Vec<&str> = factory
    .segment_spans(text)              // 产出 Span { begin, end, lexeme_type }
    .map(|s| s.slice(text, &map))     // 零分配切出原文
    .collect();
assert_eq!(words, ["欢迎", "使用", "本", "分词器"]);
```

`Span` 是 `Copy` 的位置区间：`begin()` / `end()` / `length()` / `lexeme_type()`，
坐标是**全局 `char` 下标**（跨缓冲页连续）。词元序列与 `segmenter()` **完全一致**
（同一推进逻辑，停用词过滤与数量词合并行为相同）。

| | `segmenter()` | `segment_spans()` |
|---|---|---|
| 产出 | `Lexeme`（含 `String` 文本） | `Span`（仅位置 + 类型） |
| 每词元堆分配 | 1 次 | **0 次** |
| 实测分配次数 | 205,307 (0.711/char) | **2,959 (0.010/char)** |
| 实测分配字节 | 11.79 MiB (42.8/char) | 10.24 MiB (37.2/char) |
| 实测耗时 | 39.95 ms | **37.76 ms** |

> ⚠️ **文本语义差异**：`Span::slice` 返回**原文**子串，而 `Lexeme::text()` 返回
> **归一化后**文本（`regularize`：全角→半角，且 `enable_lowercase` 时 ASCII 小写化）。
> 故输入 `"IKAnalyzer2012"` 时，切片是 `IKAnalyzer2012` 而 `text()` 是 `ikanalyzer2012`。
> **位置与类型完全一致**。若下游需要归一化后的文本，请用 `segmenter()`。

## 8. 流式 / 大文件分词

对大文件、网络流等无法一次性装进内存的场景，用 `TokenizerFactory::segmenter_from_read`：

```rust
use std::fs::File;

let file = File::open("big_corpus.txt")?;
let mut seg = factory.segmenter_from_read(file);

for lexeme in seg {
    // 逐词处理，恒定内存
    println!("{}", lexeme.text());
}
```

- 内部增量 UTF-8 解码，能正确处理**跨缓冲区的多字节字符切分**；
- 非法 UTF-8 字节会被替换成 `U+FFFD` 而非崩溃（`src/core/char_source.rs`）；
- 读取器需满足 `Read + Send + 'static`（以支持多线程复用工厂）。

## 9. 错误处理

默认 `TokenizerFactory::new` 在词典文件不存在时会 **panic**。生产环境若希望优雅处理错误，用 `try_new`：

```rust
use ik_analyzer::{Config, TokenizerFactory, IkError};

let result = TokenizerFactory::try_new(
    Config::builder()
        .add_ext_dict_paths(&["maybe_missing.dic"])
        .build(),
);

match result {
    Ok(factory) => { /* 使用 factory */ }
    Err(IkError::FileNotFound(path)) => {
        eprintln!("词典不存在: {}", path.display());
    }
    Err(IkError::Io(e)) => { eprintln!("IO 错误: {}", e); }
    Err(IkError::InvalidEncoding(_)) => { eprintln!("词典编码非 UTF-8"); }
    _ => {}
}
```

错误类型区分 `Io` / `FileNotFound` / `InvalidEncoding`（见 `src/error.rs`），比原版抛 `RuntimeException` 或静默吞掉更可控。

### 9.1 流式读取失败的判定（`take_error`）

`Iterator<Item = Lexeme>` 无法返回错误，因此流式分词在**读取出错**时只能停止并返回
已读到的部分 —— 即**内容被截断**。此时应显式判定：

```rust
use ik_analyzer::{Config, TokenizerFactory};
use std::fs::File;

let factory = TokenizerFactory::new(Config::builder().build());
let mut seg = factory.segmenter_from_read(File::open("huge.log")?);

let tokens: Vec<String> = seg.by_ref().map(|l| l.text().to_string()).collect();
if let Some(e) = seg.take_error() {
    // 读取出错：tokens 内容可能不完整，按业务决定是否接受
    eprintln!("读取失败（内容可能截断）: {e}");
}
```

也可用 `seg.has_error()` 做只读查询（可重复调用）。此外错误仍会打一条
`log::error!`，但**不要只依赖日志** —— `env_logger` 是 optional feature，
下游 crate 默认没有任何日志输出。

## 10. 多线程与并发

`TokenizerFactory` 内部用 `Arc<Dictionary>` 共享不可变词典，因此可以**跨线程克隆复用**：

```rust
use std::thread;

let factory = TokenizerFactory::new(Config::builder().build());
let mut handles = vec![];

for _ in 0..4 {
    let f = factory.clone(); // 廉价：只 clone Arc
    handles.push(thread::spawn(move || {
        let words: Vec<String> = f.segmenter("并发分词测试").map(|l| l.text().to_string()).collect();
        words.len()
    }));
}

for h in handles { let _ = h.join(); }
```

- `TokenizerFactory: Clone`（仅克隆 `Arc`），多线程共享同一部词典**零拷贝、无锁竞争**；
- 每个线程内 `factory.segmenter(text)` 创建的 `IKSegmenter` 是线程本地的，互不干扰；
- 同一进程可同时存在**多部不同词典/配置的工厂**（`Arc` 隔离），原版因全局单例无法做到。

## 11. 性能最佳实践

1. **工厂只建一次**：`TokenizerFactory::new` 会加载并编译全部词典（重）；`segmenter()` 每次仅轻量分配。把 factory 放在应用生命周期顶层或全局（`lazy_static` / `OnceCell`）。
2. **复用工厂做批量**：同一 factory 可无限次 `segmenter()`，词典只在 `new` 时建一次。
3. **大文本用流式**：文本 > 几 MB 优先 `segmenter_from_read`，避免一次性读入。
4. **`judge-fast` 是默认**：默认 feature 即启用 O(n) 链模型裁决，smart 模式约 21ms、fine 模式与原版对等（可用 `examples/perf_cmp.rs` 复测）。如需回退到与原版行为逐位一致的 `judge_reference`，用 `--no-default-features` 构建。
5. **不要**用已废弃的 `IKSegmenter::new(text, use_smart)`：它每次都重建词典，开销巨大（源码标记 `#[deprecated]`）。始终走 `TokenizerFactory`。

### 13.2 基本用法

```python
import ik_analyzer as ik
```

### 13.3 `Config` 方法（与 Rust 一一对应）

| Python 方法 | 含义 |
|---|---|
| `use_smart(bool)` | 设置模式（默认 True，同 v1.0.0 / 2012_u6） |
| `enable_lowercase(bool)` | 大小写策略（默认 True = 大小写不敏感；False = 保留原文大小写） |
| `astral_mode(AstralMode)` | 补充平面字符处理模式（默认 `AstralMode.Ideographs`，见 §6.5） |
| `with_main_dict_from_paths([...])` | 整部替换主词典（文件路径） |
| `with_main_dict_from_sources([{...}])` | 整部替换主词典（详细来源） |
| `with_quantifier_from_paths / _from_sources` | 量词词典替换 |
| `with_stop_words_from_paths / _from_sources` | 停用词词典替换 |
| `add_ext_dict_from_paths([...])` | 追加扩展主词典（文件） |
| `add_ext_dict_from_text("词1\n词2")` | 追加扩展主词典（文本） |
| `add_ext_stop_word_from_paths / _from_text` | 追加扩展停用词 |
| `add_ext_quantifier_from_paths / _from_text` | 追加扩展量词 |

`with_*_from_sources` / `add_ext_*_from_sources` 接受一个 dict 列表，每个 dict 含 `{"path": "..."}` 或 `{"text": "..."}`（两者互斥）：

```python
cfg = ik.Config()
cfg.with_main_dict_from_sources([{"path": "dict/main.dic"}, {"text": "热词A\n热词B"}])
tok = ik.Tokenizer(cfg)
```

**`AstralMode` 与 u6 parity 预设**（对应 Rust §6.4 / §6.5）：

```python
# 三值枚举：Drop（= u6 严格口径）/ Ideographs（默认）/ Tokens
cfg = ik.Config()
cfg.astral_mode(ik.AstralMode.Tokens)      # emoji 也输出为词元
tok = ik.Tokenizer(cfg)
tok.segment("你好😀世界")                    # ['你好', '😀', '世界']

# IK 2012_u6 行为 parity：钉死 u6 分发词典 + 无停用词 + 大小写不敏感 + astral 丢弃
p = ik.Tokenizer.u6_parity(use_smart=True)
p.segment("这是一个中文分词的例子")          # ['这是', '一个', '中文', '分词', '的', '例子']（'的' 不过滤）
```

### 13.4 三个分词方法

| 方法 | 返回 | 说明 |
|---|---|---|
| `segment(text)` | `list[str]` | 词元文本列表（最常用） |
| `cut(text)` | `list[Lexeme]` | 带位置/类型的词元对象（含 byte 偏移） |
| `segment_batch(list[str])` | `list[list[str]]` | 批量分词，**释放 GIL 并行** |

```python
# cut：带 byte 偏移，便于还原原文位置
lexemes = tok.cut("张三123公斤")
for lm in lexemes:
    print(lm.text, lm.start, lm.end, lm.lexeme_type)
    # 例如: 张三 0 6 CN_WORD

# segment_batch：多条并行
result = tok.segment_batch(["第一条文本", "第二条文本", "第三条文本"])
# result 是 [[...], [...], [...]]
```

> `cut` 返回的 `Lexeme` 字段：`text: str`、`start: int`、`end: int`（**byte 偏移**，非字符偏移）、`lexeme_type: str`（如 `"CN_WORD"`、`"ARABIC"` 等）。

## 14. 自定义词典格式

词典为**纯文本、UTF-8 编码、每行一个词**。加载器**没有注释语法**：以 `#` 开头的行会被当作
词条加载，只有空行会被跳过。

```
深度学习
自然语言处理
ik分词器
```

- 大小写：由 `enable_lowercase` 控制（默认 `true`，对齐 2012_u6 原版行为）。
  构建期仅对 **ASCII 大写**字母归一（非全 Unicode 小写化），输入侧同样
  仅做全角→半角 + ASCII 小写化；`enable_lowercase(false)` 则词典与输入
  均保留原文大小写，严格精确匹配（此时停用词表需自行收录大小写变体）。
  例：`Config::builder().enable_lowercase(false).build()`。
- 来源：`DictSource::File(path)` 指向 `.dic`/`.txt` 文本；`DictSource::Text(str)` 直接给字符串。
- 主词典、量词词典、停用词词典三类相互独立，分别对应 `with_main_dict` / `with_quantifier` / `with_stop_words` 及其 `add_ext_*` 变体。
- 仓库自带词典位于 `dict/`（`main2012.dic`、`quantifier.dic`、`ext_stop_word/stop.dic`），自定义词建议用 `add_ext_*` 追加，避免改动默认主词表。

## 15. 进阶：feature 旗标矩阵

除默认配置外，Cargo 提供了若干 feature 旗标（见仓库 `Cargo.toml`）。通过 `--features` / `--no-default-features` 控制：

| feature | 默认 | 作用 |
|---|---|---|
| `judge-fast` | ✅ 开 | 启用链模型重写的 `judge_fast` 作为正式裁决（O(n)，smart 更快）。 |
| `judge-verify` | ❌ 关 | 保留 `judge_reference` 并与 `judge_fast` 对每个真实 cross_path 双跑逐位 assert；任何分歧直接 panic。仅验证用，有双跑耗时。**注意：差分测试本身在普通 `cargo test` 下即编译，无需开启此 feature**；此 feature 用于「在真实分词路径上强制双跑断言」的诊断场景。 |
| `env_logger` | ❌ 关 | 为 CLI（`ik-analyzer` bin）接入 `env_logger` 日志后端，使词典加载报告可见。仅 CLI 需要，库使用者无需开启。 |

常用组合：

```bash
# 回退到与原版逐位一致的 judge_reference（关闭 judge-fast 默认）
cargo build --no-default-features

# 真实路径上强制 ref/fast 双跑断言（差分验证 / 排错）
cargo run --features judge-verify --example judge_verify_stress -- benches/corpus.txt

# 量化分配量（常驻工具，无需 feature）
cargo run --release --example alloc_count
cargo run --release --no-default-features --example alloc_count   # 对照 judge_reference

# CLI 词典加载报告（需日志后端）
cargo run --release --features env_logger --bin ik-analyzer -- "研究生命起源"
```

> **分配量计量**：20260930 曾以 `probe-count` / `probe-mimalloc` 两个 feature 提供该能力，
> 但二者从未有实现代码，已作为死 feature 删除，且**未给替代物**，导致"分配量"此后无法量化
> （评审 P3-2）。现由常驻工具 `examples/alloc_count.rs` 承担：`#[global_allocator]`
> 放在 example 内部，**不需要 feature gate**，既不污染下游编译，也不占用发布产物的
> feature 语义。它同时输出 `segmenter` 与 `segment_spans` 两条路径的对照数据。
>
> `env_logger` 仅用于 CLI 诊断，不应出现在生产构建里。

## 16. 进阶：词典加载行为、冷启动与日志

### 16.1 加载行为（运行期 DAWG 构建）

默认主/停用词/量词三部词典以**纯文本 `.dic` 经 `include_str!` 内嵌进二进制**，
首次 `TokenizerFactory::new` 时在**运行期**从文本构建紧凑 DAWG（后缀去重
有向无环图）并加载——**没有预编译步骤、没有二进制词典产物、没有 build.rs**，
词典文本即全部事实源。

冷启动成本（release，桌面级 CPU，主词典 27.6 万词）：

| 场景 | 耗时 |
|---|---|
| 首次构建（进程内第一部默认词典，三词典合计） | ~62–75ms（一次性） |
| 后续 `TokenizerFactory::new`（默认词表，全局缓存命中） | ~1.6µs |
| 自定义词典（`with_*` / `add_ext_*`） | 按词表规模全量重建，不缓存 |

说明：

- 默认词典按（词典种类 × `enable_lowercase`）进程内共享（全局缓存）；
  同进程内多个 `TokenizerFactory` 用同一套默认词表时只建一次。
- 自定义词源内容可变，不走缓存，每次 `new` 全量重建；
  高频创建含自定义词典的 factory 请自行复用实例。
- 构建期峰值内存 ~52MB，完成后活内存 ~4MB
  （`/usr/bin/time -v` 显示的 RSS 会因分配器保持已释放页而偏高，属正常现象）。

### 16.2 词典加载报告

Rust 库内部通过 `log` crate 打印**词典加载报告**（类型 / 来源 / 词数 / 状态），例如：

```
[ik-analyzer-rs] Dictionary Loading Report:
  Main       | text sources (runtime-built DAWG)             | 275717 words | Loaded
  StopWord   | text sources (runtime-built DAWG)             |    101 words | Loaded
  Quantifier | text sources (runtime-built DAWG)             |    316 words | Loaded
```

首次构建时来源列为 `text sources (runtime-built DAWG)`；同进程内后续命中全局缓存时为
`embedded text (cached DAWG)`。词数为 DAWG 构建期统计的**去重真实词数**
（DAWG 后缀共享，节点数 ≠ 词数），与内嵌文本词表一致（上例为当前内置词表大小，
随词典更新而变化）。

### 16.3 日志后端

**关键点**：报告走 `log` 的 `info!` 级别。若你的应用没挂日志后端，这条报告（以及任何 `warn` 丢弃非法词典行的提示）**不会显示**。要看到它，在 `main` 早期初始化一个 log 后端即可：

```rust
use ik_analyzer::{Config, TokenizerFactory};

fn main() {
    env_logger::init();   // 或你项目里已有的 log 后端（tracing 等）
    let factory = TokenizerFactory::new(Config::builder().build());
    // ...
}
```

`env_logger` 需加入依赖：`cargo add env_logger`。

## 17. 进阶：任意 `Read` 数据源与分块不变性

`segmenter_from_read` 接受**任何**满足 `Read + Send + 'static` 的源，不限于 `File`：

```rust
use std::io::{Cursor, stdin, Read};
use std::net::TcpStream;

// 内存字符串
let r1 = factory.segmenter_from_read(Cursor::new("内存中的文本".to_string().into_bytes()));
// 标准输入
let r2 = factory.segmenter_from_read(stdin());
// 网络流（恒定内存，适合大响应体）
let stream = TcpStream::connect("127.0.0.1:8080").unwrap();
let r3 = factory.segmenter_from_read(stream);
```

**分块不变性（流式鲁棒性卖点）**：内部 `ReadCharSource` 增量 UTF-8 解码，会把跨 `read` 边界的多字节字符正确拼接。因此**无论底层每次 `read` 返回多少字节（含 1 字节极端分块），分词结果都完全一致**——这是流式路径的正确性不变量，已在 `examples/judge_verify_stress.rs`（硬断言「不同分块大小产生相同分词指纹」）中验证。

## 18. 进阶：`Dictionary` 直接 API 与基准

`factory.dictionary()` 返回 `Arc<Dictionary>`，包含底层 Trie 查询方法（如 `match_in_main_dict(&[char], begin, length)`）。这**不是日常分词所需**，而是给**基准测试 / 自定义词典算法研究**用的，例如直接测量主词典最长匹配的单步查找开销：

```rust
use ik_analyzer::Dictionary;
use ik_analyzer::Config;

let dict = Dictionary::new(&Config::builder().build());
let chars: Vec<char> = "中华人民共和国".chars().collect();
// 从位置 0 起做一步主词典匹配（CJKSegmenter 逐字最长匹配的最小单元）
let hit = dict.match_in_main_dict(&chars, 0, 1);
```

> 该 API 面向高级用户；绝大多数场景请用 `TokenizerFactory` + `segmenter()`，不要直接操作 `Dictionary`。

## 19. 进阶：examples 与 benches 指路

仓库自带可直接运行的进阶用例，适合做性能基线与一致性确认：

| 路径 | 用途 |

| `examples/alloc_count.rs` | **分配量计量**（替代已删除的 `probe-count`）：统计分词热路径的堆分配次数/字节数、每字符与每词元指标，并输出 `segmenter` vs `segment_spans`（零拷贝）对照。用法：`cargo run --release --example alloc_count [corpus.txt]` |

| `examples/perf_trie.rs` | Trie 查找耗时占比基准：把逐字最长匹配的单步 `match_in_main_dict` 耗时与完整分词耗时对照，量化词典查找占比 |
| `examples/judge_verify_stress.rs` | 一致性加压轮：对内置歧义语料 + 自定义词典维度，验证**流式不变性**（不同分块大小结果一致）与**并发确定性**（多线程指纹全等）；配合 `judge-verify` feature 还会对每个 cross_path 强制 ref/fast 双跑 assert |

## 20. 自定义停用词：会从结果中剔除

新增停用词后，匹配上的词元**不会出现在最终输出里**（不是单独成一个词元，而是被直接过滤）。源码在输出阶段判断 `is_stop_word` 后跳过（`analyze_context.rs`）：

```rust
let factory = TokenizerFactory::new(
    Config::builder()
        .add_ext_stop_word_owned_text("的\n了".to_string())
        .build(),
);

let words: Vec<String> = factory.segmenter("我的书").map(|l| l.text().to_string()).collect();
println!("{:?}", words); // ["我", "书"]  —— "的" 被过滤掉了
```

> 这与原版 IK Analyzer 行为一致：「停用词」是输出级过滤，而非建索引时的「不索引但保留」。若你业务需要「保留但标记」，应改用自定义词典而非停用词。

## 21. 常见问题（FAQ）

**Q：为什么我直接用 `IKSegmenter::new(text, true)` 编译有 deprecation 警告？**
A：该方法每次调用都重建词典，开销大，已被废弃。请改用 `TokenizerFactory::new(config).segmenter(text)`。

**Q：`segmenter(text)` 每次都要重新加载词典吗？**
A：不需要。`TokenizerFactory::new` 时加载一次并编译进 `Arc<Dictionary>`；此后 `segmenter()` 每次仅做轻量分配。

**Q：smart 和 fine 该选哪个？**
A：需要语义清晰、结果简洁（如文本展示、关键词）用 smart；需要高召回、建倒排索引用 fine。两者分词质量与原版一致。

**Q：能否同时跑多个不同词典的工厂？**
A：可以。`Arc<Dictionary>` 隔离，同一进程可并存多部不同配置的工厂（原版全局单例做不到）。

**Q：补充平面生僻字（如 `𪚥`）能识别吗？**
A：能，且行为可配置（`AstralMode`，见 §6.5）。默认 `Ideographs`：CJK 扩展 B–I 识别为汉字（原版 Java `char` 是 UTF-16 码元，>U+FFFF 会被拆成代理对丢弃）；emoji 等其余补充平面字符默认丢弃，`AstralMode::Tokens` 可输出为词元；`AstralMode::Drop` 即 u6 严格口径（`Config::u6_parity` 钉此值）。

**Q：`begin_position`/`end_position` 是什么单位？和 Java 原版能直接比较吗？**
A：Rust 核心为**码点（Unicode scalar）下标**，Python `cut` 为 **byte（UTF-8）偏移**；
Java 原版是 **UTF-16 code unit**。三者**不可直接比较**：与 Java 差分时须换算
（码点 → UTF-16：BMP 1:1，astral 1→2）。词元的**文本与类型序列不受单位影响**，
parity 契约以词元序列为准（见 §6.4 例外清单 #4）。

**Q：Python 用 `cut` 的 `start/end` 是字符还是字节偏移？**
A：是 **byte（UTF-8）偏移**，便于直接用 Python 字符串切片定位原文。

**Q：如何回退到与原版逐位一致的裁决实现？**
A：默认已是 `judge-fast`（O(n)，smart 更快）。如需 `judge_reference`，构建时 `--no-default-features` 即可。

**Q：CLI 不传 `--custom-dict` 时会用 IK 默认主词典吗？**
A：会。CLI 未指定自定义词典时，自动加载仓库自带默认主词典。
